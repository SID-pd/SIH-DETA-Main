How RailPulse Works: Real-Time Dynamic ETA Prediction & Graph Operational Intelligence

Traditional railway ETAs rely on static timetable extrapolations and fixed recovery buffers, leaving operations blind to en-route signal halts, micro-valley fog, and cascading precedence delays. RailPulse replaces static timetables with an adaptive cyber-physical railway graph that decouples historical statistical behaviour, real-time machine learning inference, and strict physical railway constraint verification.

Methodology 01

Time-Dependent Graph Representation

The railway network is modeled as a topological graph where nodes represent stations, junctions, and intermediate halts, while edges represent block sections parameterized with live speed restrictions (TSR), gradients, and signal aspects.

Methodology 02

Adaptive Dual-Mode Traversal

Computes aggregate section ETAs during nominal traffic flow. The moment an unexpected halt or delay variance occurs, the engine dynamically explodes into Halt-by-Halt Detailed Traversal to isolate hyper-local bottleneck causes.

Methodology 03

3-Layer Decoupled Intelligence

Strictly separates empirical dwell DNA (Layer 1), dynamic gradient-boosted time-series inference (Layer 3), and physical railway safety & headway verification (Layer 2) to ensure all predicted arrival times are mathematically feasible.

Methodology 04

High-Throughput Tiered Storage

PostgreSQL + PostGIS serves as the authoritative, private source of truth for graph topology and audits, while an in-memory Redis cluster delivers sub-1.5ms cached reads to withstand millions of concurrent IRCTC queries without database lockup.

Algorithmic Working Methodology

Dual-Mode Railway Network Traversal Logic

How RailPulse balances extreme computational efficiency during normal operations with deep explainable micro-traversal when disruptions occur.

Mode 1: Normal Section Mode

Low Compute Overhead
T_section = Distance / V_mps + W_dwell(station)

Applied when trains run nominally within scheduled tolerances. The model computes aggregate block section transit times without inspecting intermediate signal aspects or micro-climatic sensors.

  • Zero unnecessary CPU/memory expenditure across thousands of on-time trains.
  • Calculates ETAs in sub-millisecond batch operations.
  • Continuously monitors variance threshold: Δ = |T_live - T_predicted|.

Mode 2: Detailed Halt Traversal

High Precision Micro-Scan
T_total = ∑ [ T_segment,i + D_halt,i + ΔT_fog,i + ΔT_signal,i ]

Triggered automatically when delay variance exceeds threshold (Δ > 3 min) or when localized sensors alert. Explodes the section into individual halt nodes, evaluating micro-weather and speed restrictions.

  • Pinpoints the exact geographical source of disruption (e.g. 12 km fog valley).
  • Prevents propagating a localized halt delay uniformly across the entire corridor.
  • Forecasts realistic downstream speed recovery through Layer 1 buffer models.

Mathematical & Rulebook Foundations

The 3-Layer Prediction & Verification Architecture

How RailPulse decouples statistical empirical training, machine learning time-series inference, and railway physical safety constraints.

01 Statistical & Empirical Model

Layer 1: Behaviour Analysis

W_dwell = f(Train_type, Station_category, Day_of_week)

Learns the empirical behavioural DNA of trains and stations from historical archives. A premium Rajdhani express at a terminal junction has fundamentally different dwell characteristics than a passenger rake during morning peak hours.

OUTPUT: Behavioural Weight Vector (W_dwell, W_recovery)
03 Gradient Boosted Time-Series Model

Layer 3: Dynamic ML ETA Model

P(ETA_t) = ML(GPS_coords, Speed, Weather_matrix, W_layer1)

Continuous regression model (LightGBM/PyTorch) ingesting live RTIS telemetry, instantaneous speed, Layer 1 weights, and micro-weather indices (visibility, rain adhesion). Outputs probabilistic arrival distributions with confidence scores.

OUTPUT: Raw Probabilistic Forecast: PRYJ 23:48 ± 2.1m (92% Conf)
02 Physical Railway Safety Rulebook

Layer 2: Constraint Verification

∀ rakes (A, B): t_arrival(B) - t_arrival(A) ≥ Headway_min

Enforces railway physical realities. Evaluates block section availability, braking deceleration curves, and platform conflicts. If the ML model predicts an ETA that would violate minimum headway, Layer 2 rejects it and computes feasible precedence.

OUTPUT: Verified Feasible ETA & Safe Platform Routing

Storage Paradigm: Main Database vs. Redis In-Memory Tier

The architectural reason RailPulse maintains sub-millisecond query responses under nationwide load without risking persistent database failure.

💾

Master Database (PostgreSQL + PostGIS)

Persistent Source of Truth

Strictly private and shielded from public traffic. Stores static and slow-changing operational assets: master timetable schedules, PostGIS track line strings, station platform track layouts, crew shift rosters, and historical run logs.

Data Format Relational Tables + PostGIS LineStrings
Access Pattern Private Batch Reads & Offline Model Training
Concurrency Target Internal Microservices (Zero Public Exposure)
Durability Guarantee ACID Compliant Disk Persistence
⚡

Redis In-Memory Key-Value Tier

High-Throughput Public Serving

Holds transient live state in RAM to serve tens of millions of public passenger app queries (NTES, IRCTC) and platform boards with sub-1.5ms read latency, completely isolating the PostgreSQL disk from read spikes.

Data Format In-Memory Hashes & Sorted Sets
Read Latency < 1.5 ms Direct from RAM
Throughput Capacity 100,000+ Concurrent Queries / Sec
Refresh Trigger Pub/Sub Stream from Layer 2 Verification
